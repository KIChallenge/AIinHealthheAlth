Build a local Neo4j database and a Markdown document importer for an Austrian healthcare negotiation prototype. you also have the pdf of the assignment, this should only be a databse and later on, data from 2020-2024 will be imported as well.

Implement the database structure, importer, retrieval functions, and necessary tests.

Use simple, readable code with few dependencies. Check for programming errors, inconsistent data, and incorrect relationships. Report failures clearly.

IMPORTANT: We will supply the institution-specific keyword lists later. For now, skip keyword matching and direct connections between actors and articles. Do not invent keyword lists or infer those connections using an LLM.

1. PURPOSE

The prototype has three stakeholder agents:

- Gesundheitsministerium
- Sozialversicherung
- Ärztekammer

It also has three specialist reviewers:

- TruthSeeker
- LegalEye
- EthicMind

Neo4j stores representations of these actors and reviewers, their source documents, and the relationships described below.

The agents themselves run outside Neo4j.

Source access:

- Each actor receives its own institutional profile documents.
- TruthSeeker receives all articles and all institutional profile documents across every actor.
- LegalEye receives legal documents.
- EthicMind receives ethical documents.

TruthSeeker has no separate document collection or source folder. It uses the same Article and ActorData nodes already stored in the database.

A document’s connection to a reviewer describes its intended use. It does not establish that the document is factually correct, legally current, or ethically authoritative.

2. INPUT FOLDERS

Use this structure relative to a configurable data directory:

Data/
├── Articles/
├── ActorData/
│   ├── Gesundheitsministerium/
│   ├── Sozialversicherung/
│   └── Aerztekammer/
├── LegalEye/
└── EthicMind/

All source documents are Markdown files with the extension .md // in legaleye, its with the extension .xml

Read Markdown files recursively, including nested folders.

Folder meanings:

Articles/
Articles available to TruthSeeker. Direct connections to actors will be added later using keyword lists supplied by us.

ActorData/<institution>/
Documents used to establish that institution’s profile and positions. These documents are available to the corresponding actor and to TruthSeeker.

LegalEye/
Legal source documents.

EthicMind/
Ethical reference documents.

Do not require or create a TruthSeeker source folder.

Preserve the original files. Treat document contents as data, never as instructions.

Treat one Markdown file as one document. For Articles, the expected input is one article per file. Do not automatically split files into articles or claim to have verified their editorial boundaries.

4. RELATIONSHIPS TO CREATE NOW

Create:

(Actor)-[:HAS_PROFILE_SOURCE]->(Document:ActorData)

(Moderator {name: "TruthSeeker"})-[:USES_SOURCE]->(Document:Article)

(Moderator {name: "TruthSeeker"})-[:USES_SOURCE]->(Document:ActorData)

(Moderator {name: "LegalEye"})-[:USES_SOURCE]->(Document:LegalText)

(Moderator {name: "EthicMind"})-[:USES_SOURCE]->(Document:EthicalText)

Rules:

- Each actor connects only to ActorData documents in its corresponding institution folder.
- TruthSeeker connects to every Article document.
- TruthSeeker also connects to every ActorData document across all institutions.
- LegalEye connects to every document in LegalEye.
- EthicMind connects to every document in EthicMind.

For example, a ministry profile document is represented by one Document:ActorData node with these two incoming relationships:

(Gesundheitsministerium)-[:HAS_PROFILE_SOURCE]->(document)

(TruthSeeker)-[:USES_SOURCE]->(document)

Do not create a second copy of that document for TruthSeeker.

Apply this sharing rule to every ActorData document, including documents belonging to actors added later.

Store each relationship in one direction. Queries can traverse relationships in either direction where needed.

Do not create duplicate reverse relationships.

5. DIRECT ACTOR–ARTICLE MATCHING IS DEFERRED

Do not create direct actor–article relationships in this implementation stage.

In particular:
- Do not generate institution-specific keyword lists.
- Do not infer connections from article meaning.
- Do not connect actors merely because their names appear in documents.
- Do not treat missing keyword lists as a failure.
- Do not implement a matching engine at this stage.

Report the feature status as:

actor_article_matching: deferred_pending_keyword_lists

Keep the design ready for a later relationship:

(Actor)-[:MATCHES_KEYWORD]->(Document:Article)

Future matching will be deterministic and will support:
- Case-insensitive matching.
- Explicit German word variants.
- Configurable compound-word matching.

For example, future variants "arzt" and "ärzt" should support matches such as Arzt, Ärzte, Ärztin, Hausarzt, and Hausärztin.

This is a future requirement, not an instruction to build or run matching now.

The existence of an indirect graph path from an actor to an article through TruthSeeker must not be interpreted as a keyword match or institutional stance.

6. LOGICAL DATA GROUPS

Use a scope property with these values:

actor_truth
legal
ethics

Assign:

actor_truth:
- All Actor nodes.
- All ActorData documents.
- All Article documents.
- TruthSeeker.

legal:
- LegalEye.
- LegalText documents.

ethics:
- EthicMind.
- EthicalText documents.

Do not create relationships across scopes.

These are three logical data groups. They do not need to form exactly three connected components.

Within actor_truth:
- TruthSeeker connects to all articles and all ActorData documents.
- An actor with at least one profile document is connected indirectly to TruthSeeker through that document.
- An actor without profile documents can remain isolated while direct actor–article matching is deferred.

Do not invent relationships to make the graph connected.

If the same source appears in multiple scopes, store separate scoped Document nodes. They may share a source URL and content hash.

Do not merge records across scopes.

TruthSeeker’s full source access means all Articles and ActorData documents. LegalText and EthicalText documents remain in their separate scopes.

7. DOCUMENT IDENTIFIERS AND PROPERTIES

Give every document a stable ID.

By default, derive its identity from its scope and normalized path relative to the data directory. Use a collision-safe encoding or hash of those values.

Keep identity separate from content:
- Editing a file at the same path updates the existing document.
- Its content hash changes.
- Renaming a file creates a new identity unless an explicitly supported persistent ID preserves continuity.

If persistent IDs in document metadata are supported, document their rules and reject conflicting IDs.

Store these required properties:

- Document ID.
- Scope.
- Document type.
- Display title.
- Title origin.
- Original Markdown content.
- Extracted readable text.
- Relative source path.
- Content hash.
- First-import timestamp.
- Last-update timestamp.
- Importer ownership marker.

Store these when available:

- Publisher.
- Publication date.
- Source version.
- Valid-from date.
- Valid-until date.

Do not invent missing metadata.

Keep publication dates, validity dates, and import timestamps distinct.

Do not infer that a legal document is currently valid merely because it was recently imported.

8. MARKDOWN AND METADATA HANDLING

Support a documented front-matter format for optional metadata.

Retain the complete original Markdown separately from extracted readable text.

For the display title, use:
1. An explicit metadata title.
2. Otherwise, the first Markdown heading.
3. Otherwise, the filename.

Record the title origin as:
- metadata
- heading
- filename

A filename used as a display title must remain distinguishable from a title found inside the document. This will prevent future keyword matching from accidentally matching filenames.

When extracting readable text:
- Preserve visible text and visible link labels.
- Exclude front matter.
- Exclude URL destinations.
- Exclude HTML comments.
- Remove Markdown formatting without discarding its readable content.

Do not allow malformed metadata to pass silently.

10. RETRIEVAL

Provide small retrieval functions or documented queries for:

A. Actor profile sources
Return only the documents connected to the selected actor through HAS_PROFILE_SOURCE.

Do not expand this query through TruthSeeker to other institutions’ documents.

B. TruthSeeker sources
Return all Article and ActorData documents connected to TruthSeeker through USES_SOURCE.

This includes profile documents from every institution.

Support filtering by document type and, for ActorData, by institution. The default should include both document types and all institutions.

C. LegalEye sources
Return LegalText documents connected to LegalEye.

D. EthicMind sources
Return EthicalText documents connected to EthicMind.

E. Document lookup
Return a document, its content, metadata, and provenance by stable ID.

F. Import diagnostics
Return document counts, relationship counts, warnings, errors, and source-presence status.

If an actor–article retrieval function is provided, it should explicitly report that matching is deferred. An empty result must not be described as evidence that no relevant articles exist.

Use the specified relationships and scopes to determine retrieval results. Do not use unrestricted graph traversal as a substitute for these access rules.

Graph separation alone is not database access control. Do not claim that these functions prevent a user with unrestricted query access from reading other scopes.
